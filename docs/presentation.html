Une application pour gérer les concerts d'une agence de musiciens

Un agent artistique place des pianistes et des violonistes en concert. Cette application l'aide à suivre chaque concert, de la première demande d'une salle jusqu'au soir où il est joué. Chaque musicien, lui, consulte ses propres concerts.

En ligne : agence-musiciens.vercel.app · code : github.com/ValentinWIA/agence-musiciens · toutes les données sont fictives.

01Qui utilise l'application ?

Deux sortes de comptes, et une troisième catégorie de personnes qui n'en a pas.

Agent

L'administrateur

Voit et modifie tout. Invite les musiciens, crée les concerts, fait avancer leur statut, ajoute les contrats en PDF.

Musicien

Pianiste ou violoniste

Ne voit que ses propres concerts, sans pouvoir les modifier ni voir les coordonnées des salles.

Sans compte

Les programmateurs

Salles et festivals qui demandent un concert. Ce sont des données (des contacts), pas des utilisateurs.

02La vie d'un concert

Le cœur du produit : un concert passe par des étapes, toujours dans le même ordre. L'application refuse les sauts illogiques et explique pourquoi.

Demande→ Option→ Contrat envoyé→ Confirmé→ Joué
Annulé↺ peut être rétabli : le concert revient à l'étape où il était.

Une « option »

La salle réserve une date sans s'engager encore. Il faut alors une date précise et une durée.

Verrouillage

À partir de « confirmé », on ne peut plus changer la date, le lieu ni le cachet : seulement le titre, le programme et les notes.

Conflit d'agenda

Un musicien ne peut pas être confirmé à deux concerts trop proches : l'application estime le trajet entre les deux villes.

Pourquoi des « règles » à part ? Toutes ces vérifications sont écrites comme de petites fonctions indépendantes de l'écran et de la base de données. On peut donc les tester automatiquement, en quelques millisecondes, à chaque modification du code.

03Comment c'est construit

Quatre couches, comme quatre pièces d'une maison. Chacune a un rôle, et elles se parlent dans un ordre précis.

1 · Interface

  • Le navigateur
  • Pages et formulaires (React)
  • Ce que l'on voit

2 · Serveur

  • Next.js, hébergé sur Vercel (Francfort)
  • Vérifie les droits
  • Applique les règles

3 · Données

  • Base Postgres (Neon)
  • PDF privés (Vercel Blob)

4 · Services externes

  • IGN : adresses et coordonnées GPS
  • Resend : envoi des courriels

L'interface ne parle jamais directement à la base : tout passe par le serveur, qui contrôle.

Le trajet d'un clic : l'agent crée un concert

  1. L'agent clique sur « Créer ». Le navigateur envoie les champs du formulaire au serveur.
  2. Le serveur demande : qui es-tu ? Il lit le cookie de session, signé avec une clé secrète. Pas d'agent ? Refus, noté dans le journal.
  3. Il vérifie la saisie. Montant valide, date complète et pas dans le passé, lieu et musiciens qui existent vraiment en base.
  4. Il écrit en base, tout ou rien. Le concert et ses musiciens sont enregistrés ensemble ; si une partie échoue, rien n'est écrit.
  5. Il répond. Succès : la fiche s'ouvre. Refus : chaque erreur s'affiche sous le bon champ, la saisie est conservée.

04La sécurité en quatre idées

Pas besoin d'être expert pour comprendre l'essentiel : il s'agit surtout de ne jamais faire confiance au navigateur.

Cacher ≠ protéger

Si Louis tape l'adresse d'un concert d'Anna, le serveur vérifie à chaque requête et répond « introuvable ». La tentative est notée dans le journal.

Rien à deviner

Chaque élément a un identifiant aléatoire (UUID) : on ne peut pas passer de /engagements/7 à /engagements/8.

Empreintes, pas secrets

Les mots de passe et les liens d'invitation ne sont pas stockés tels quels, mais sous forme d'empreinte : impossible de remonter à l'original.

Clés hors du code

Les clés (courriels, session) vivent dans Vercel, pas sur GitHub. On peut les changer sans toucher au code : c'est la « rotation ».

05La méthode de travail

Le même cycle pour chaque fonctionnalité, de l'idée à la mise en ligne.

  1. Cadrer par écrit. Ce qu'on construit, les règles, ce qui est hors périmètre (SPEC.md, docs/).
  2. Une branche par fonctionnalité. On travaille à côté de la version en ligne, sans la toucher.
  3. Commit puis push. Le commit enregistre une version sur l'ordinateur ; le push l'envoie sur GitHub.
  4. Vérifications et prévisualisation. GitHub lance les tests ; Vercel crée un site de test avec sa propre base.
  5. Vérifier « au geste ». Un humain essaie vraiment, en agent puis en musicien. Plusieurs bugs ont été trouvés ainsi.
  6. Pull request et fusion dans main. C'est seulement là que la production change.

Travailler avec une IA. Le code a été écrit avec Claude Code. L'humain cadre, décide, vérifie chaque étape et garde la main sur tout ce qui touche la production : les garde-fous de l'outil refusent d'ailleurs à l'IA de lire la base réelle ou de fusionner seule.

06Ce que j'en retiens

L'ordre compte

Une migration se joue avant le chargement des données : on remplit d'abord, on impose la contrainte ensuite.

Tester en vrai

« Paris 75013 » et « 75013 Paris » laissaient passer un doublon de lieu : seul l'essai à la main l'a montré.

Un bug discret

La police prévue n'était jamais utilisée, à cause d'une variable qui renvoyait à elle-même. Le site semblait juste « bâclé ».

Et ensuite

Jours fériés (avertissement si un concert tombe un jour férié du pays), conversion des cachets en euros (taux de la Banque centrale européenne), limite d'essais de connexion, suivi des erreurs (Sentry), puis l'IA dans le produit en semaines 3 et 4.

07Petit glossaire

Serveur
l'ordinateur distant qui exécute le code et décide ; le navigateur ne fait qu'afficher et envoyer.
Base de données
l'endroit où les informations sont rangées en tables (concerts, lieux, musiciens…).
Migration
un fichier qui modifie la structure de la base, rejoué dans le même ordre partout.
Branche
une copie de travail du code, pour développer sans toucher la version en ligne.
Prévisualisation
un site de test créé automatiquement pour chaque branche.
Production
la vraie version en ligne, celle de la branche main.
Cookie de session
une petite carte d'identité signée que le navigateur présente à chaque requête.
Empreinte (hachage)
un résumé à sens unique d'un secret : on peut comparer, jamais retrouver l'original.
Clé d'API
un mot de passe réservé aux programmes, pour utiliser un service extérieur.
IDOR
faille où l'on accède aux données d'un autre en changeant un identifiant dans l'adresse.
